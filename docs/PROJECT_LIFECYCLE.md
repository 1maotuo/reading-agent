# 九阶段开发路线与 Gate

- 路线版本：`0.3`
- 日期：2026-09-09
- 原则：每一阶段必须产生可检查的产物、证据和Gate结论；不满足门槛不得自动推进。

## 总览

| 阶段 | 名称 | 核心目标 | 当前状态 |
|---|---|---|---|
| 00 | 立项与风险分级 | 确认为什么做、给谁做、风险是否可接受 | 已完成（设计确认） |
| 01 | 需求调研与问题定义 | 把“想做阅读AI”收敛为真实用户问题 | 已完成（设计确认） |

## 00 立项与风险分级

### 目标

- 确认产品服务的用户和问题，而不是为了展示技术而立项。
- 识别版权、隐私、跨用户隔离、模型幻觉、成本和外部平台依赖。
- 决定风险处理方式以及不可逾越的边界。

### 产物

- `docs/PRODUCT_SPEC.md`
- `docs/RISK_REGISTER.md`
- 项目范围与非目标

### Gate 00

- 核心用户和问题明确。
- 用户只上传自己有权使用的文件，系统不提供公共书库。
- 数据存储、删除和第三方模型传输边界明确。
- 风险有负责人或处理策略，没有无法接受的未知高风险项。

### 当前结论

设计层面已确认，风险等级暂定R3（中等）：项目处理用户私有书籍和阅读数据，并调用外部模型，但第一版没有高危写操作和公开内容分发。

## 01 需求调研与问题定义

### 目标

- 明确用户为什么会放弃难书，以及现有阅读软件和通用聊天工具没有解决什么。
- 确认首版用户旅程和产品核心体验。

### 产物

- 问题陈述、目标用户、核心旅程和范围。
- 竞品能力只作为参考，不用“功能更多”代替真实需求。

### Gate 01

- 能用一句话说明产品解决的问题。
- 至少一个端到端用户场景能够被演示。
- 核心不是普通摘要、翻译或智能客服。

### 当前结论

已确认核心是“在网页阅读过程中，AI结合原文证据、当前进度和稳定偏好帮助用户理解”，而不是替用户读完整本书。

## 02 AI能力边界与成功标准

### 目标

- 区分确定性代码、检索、模型判断和外部工具的职责。
- 定义回答质量、证据、安全、同步和失败场景的成功标准。

### 产物

- 第一版成功定义。
- AI能力边界和非目标。
- 初始验收标准。

### Gate 02

- 模型不直接处理整本书，不执行任意代码。
- 回答可绑定原文；证据不足时明确说明。
- 系统不推断用户智力或虚构理解状态。
- 第一版的必须项和延期项已经分开。

### 当前结论

设计层面已完成，详见产品说明和架构草案。

## 03 技术栈选型与可行性试验

### 目标

- 不靠“理论上能做”，用最小代码验证四个高风险点。
- 只有试验结果满足门槛，相关技术才正式进入基线。

### 试验

1. 四类文件能否解析为统一Block并保留来源锚点。
2. PostgreSQL、pgvector、关键词、向量、RRF和重排能否形成可运行检索链路。
3. 主模型能否稳定产生受控工具调用，并通过SSE返回结果。
4. 网页划线能否在刷新、字体变化和窄屏下恢复。

### 产物

- `docs/FEASIBILITY_PLAN.md`
- `experiments/`中的最小试验代码和样本说明
- `artifacts/feasibility/`中的测试报告

### Gate 03

- 四项试验均有可复现命令、退出状态和结果证据。
- 未通过项有替代方案或明确阻塞，不以模拟结果冒充真实验证。
- 技术选型根据证据修订并形成版本。

### 当前结论

四项最小试验均已执行。F-03-01已补充1份真实EPUB和1份228页文字型PDF，重复解析稳定且24/24抽样来源锚点恢复通过，但复杂双栏、表格、公式、脚注和异常EPUB仍未验证；F-03-03与F-03-04也已在明确的实验边界通过。F-03-02真实PostgreSQL＋pgvector约10k试验的四路、范围oracle、重复p95和EXPLAIN/索引硬门通过，并完成一次有界独立审计。因此Gate 03在限定实验边界通过，不代表生产负载或后续Gate自动通过。

## 04 架构与契约设计

### 目标

- 把架构草案转换为前后端都能直接实现和测试的契约。
- 固定模块边界，避免开发中重复争论同一问题。

### 产物

- 数据库实体关系与迁移策略。
- Book、Block、Chunk、EvidenceBundle、ContextPackage和Trace模型。
- REST、SSE和错误响应契约。
- 六个工具的输入输出Schema。
- 后台任务状态、重试、取消、检查点和原子发布契约。
- 权限、删除和日志脱敏契约。

### Gate 04

- 关键数据结构可以通过Schema验证。
- API、工具、SSE状态和错误码有示例及契约测试。
- 任何模块都不需要读取另一个模块的内部实现才能正确调用。
- 架构与第03阶段验证结果一致。

### 当前结论

已冻结并实现C01至C18最小契约包。当前源码自测25/25、C01至C18映射、OpenAPI/六工具Schema双次确定性、DDL静态一致性和一次独立只读审计11/11均通过。C18按冻结计划仍只做DDL静态审查，不把生产PostgreSQL Repository、对象存储或持久Worker混入本Gate。Gate 03已经在限定实验边界通过，故Gate 04在冻结契约边界正式通过；生产适配器和真实纵向闭环转入Stage 05正式工作。

## 05 具体功能与纵向切片开发

### 目标

先打通最小闭环，再扩展格式、语音和联网功能。

### 首条纵向切片

```text
登录 → 上传一本书 → 后台解析 → 网页阅读
→ 划线提问 → 书内检索 → 流式证据回答
→ 保存进度、划线、对话和必要偏好
```

### 产物

- 可运行前端、API、Worker和数据库迁移。
- 自动化单元与集成测试。
- 本地一键启动说明。
- 每个功能对应完成条件和证据。

### Gate 05

- 纵向闭环在全新环境中按文档能够启动。
- 不使用硬编码演示数据冒充真实链路。
- 关键失败路径可见且不会产生半成品发布。
- 功能状态与真实实现、测试证据一致。

### 当前结论

上传、解析、网页阅读、进度、划线、书内证据问答、SSE与引用回跳已形成可操作的本地开发预览；SQLite开发适配器可在服务重启后恢复书籍、正文、进度、划线、证据、问答和终态任务；PostgreSQL核心读写/事务、EvidenceRef、JobStore及问答历史/SSE replay已有窄范围数据适配证据，但尚未接入现有 API/Runtime。持久化审计发现的并发旧快照覆盖与敏感会话数据落盘两项P1已集中修复，并以定向3/3、Stage05核心7/7和`compileall`复验。该结论不代表独立Worker部署、生产对象存储、真实多端同步、复杂真实书籍或Gate 05正式通过。

## 06 评测、安全测试与调优

### 目标

- 量化检索、工具、证据、个性化、延迟和成本。
- 检查跨用户隔离、提示注入、剧透边界和异常降级。

### 产物

- 初始80至120条高质量场景测试集。
- 检索、工具、证据和回答评测报告。
- 安全与权限测试报告。
- 性能、Token和费用基线。
- Badcase分类及回归集。

### Gate 06

- P0安全用例全部通过。
- 引用必须定位到真实Block并支持关键结论。
- 修改后的Badcase与完整回归集均通过约定门槛。
- 延迟和费用未超过设定预算。
- 已知缺陷被记录、分级并有明确处理决定。

### 当前结论

已建立30项开发预览确定性检查，覆盖身份与CSRF、四格式上传、阅读、幂等、进度、划线、删除、证据回答、SSE断点续传、Trace、模型失败降级、跨用户隔离和SQLite恢复安全。最终30/30通过，定向回归16/16及前端构建通过，Sol有界审计无P0/P1并记录3项P2。由于尚未执行真实模型回答质量、提示注入攻防、约10k pgvector性能、Token费用和真实多设备评测，Gate 06不正式通过。

## 07 定型发布与产品化

### 目标

- 从开发原型转为可持续运行的小规模产品。

### 产物

- Docker Compose生产部署。
- 域名、HTTPS、ICP备案和必要的公安联网备案。
- 私有OSS、备份、恢复演练和预算告警。
- 正式微信登录；密码登录保留，手机号登录接口预留或实现。
- 发布版本、变更记录、回滚方案和用户说明。

### Gate 07

- 生产环境通过健康检查和核心E2E测试。
- 数据库和对象存储备份可恢复。
- API密钥不进入前端、仓库或Trace。
- 微信登录、删除流程和多端同步通过真实环境验证。
- 有明确回滚版本和操作方法。

## 08 运营、学习与退役

### 目标

- 根据真实用户行为改进产品，而不是根据想象持续堆功能。
- 控制模型、搜索、语音和存储成本。
- 产品停止、迁移或替换服务时，用户数据可导出并安全删除。

### 产物

- 运营指标、失败趋势和用户需求记录。
- 候选Prompt、Skill和检索策略的受控评测流程。
- 版本支持与迁移政策。
- 数据导出、账号删除和产品退役方案。

### Gate 08

- 线上问题能够通过Trace定位并进入回归集。
- 系统级优化经过评测和人工审批，且可以回退。
- 成本、错误率和关键体验指标有监控和阈值。
- 退役时能停止新写入、导出用户数据、删除云端内容并保留必要的合规记录。

## 阶段推进规则

1. 当前主阶段只能有一个。
2. 后续阶段允许预研，但不得在前置Gate未通过时声明完成。
3. 每个Gate必须引用新鲜证据；“看起来能用”不是证据。
4. 用户改变产品路线时，先记录决定、影响和被替代方案，再修改实现。
5. 未通过的试验和测试必须保留真实状态，不为了推进阶段而改写结论。
6. MVP默认采用`docs/VERIFICATION_POLICY.md`的严格但有界策略：冻结范围、一次实现自测、一次独立验收；P0/P1阻断，P2进入待办；外部阻塞不妨碍无依赖草案推进。

# 严格但有界的验证策略

- 生效日期：2026-09-08
- 适用阶段：个人产品原型、MVP与后续迭代
- 用户确认：保留测试、独立审计和执行证据，同时优先尽快形成可用版本

## 核心原则

1. 开发前冻结本工作包的验收范围；复核时发现的新边界问题按严重级别登记，不无限扩大本轮标准。
2. P0/P1阻断当前工作包；P2进入待办，除非它直接影响当前核心用户链路，否则不阻断首版。
3. 外部环境阻塞只记录一次。未验证部分不得宣称通过，但不影响无依赖模块以“草案/未验收”状态继续推进。
4. 每个工作包默认只有一次实现自测和一次独立验收。修复P0/P1后，只复跑失败用例与核心回归，不重新审计整库。

## 默认分工

- 实现与自测：Luna Max；范围限定到明确文件、验收标准和测试命令。
- 独立验收：Sol High或Max；只读变更文件、关联合同和证据，不默认读取整个项目。
- Ultra：仅在重大架构决策、生产发布、安全与隐私高风险变更时由用户或主任务明确启用。
- 小改动：由主任务直接实现和验证，不为形式上的多角色拆分额外任务。

## 最小证据

每个工作包只保留：验收范围、运行命令、真实退出码、关键测试数量、必要哈希、已知限制和结论。测试输出与详细探针保存在制品中，治理账本只引用摘要，不重复抄写长报告。

## 停止条件

- 冻结范围内的核心测试通过且无P0/P1，即停止本轮验证。
- 依赖不可用时记录阻塞与解除条件，停止重复探测。
- 新发现的非阻断优化进入P2待办，留到真实用户反馈或对应阶段处理。
